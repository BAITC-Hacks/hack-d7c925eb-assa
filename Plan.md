# Career Quest — план следующей итерации

Обновлено: 23 сентября 2026 года. Статус: план; реализация этой итерации ещё не начата.

Документ заменяет первоначальный план сборки MVP за 20–30 минут. Базовое приложение уже существует. Дорабатываем его небольшими законченными этапами, сохраняя Next.js → FastAPI → SQLite и Recommendation Engine. ARCHITECTURE.md не меняем.

## 1. Две проблемы и доказуемые решения

### Проблема 1. Сотрудник не понимает свой уровень и следующий полезный шаг

В кейсе разрозненные HR-события не связаны для сотрудника с карьерной целью. Описанные последствия — формальное обучение к дедлайну и низкая явка на добровольные активности. Главный вопрос пользователя: «Где я сейчас, чего мне не хватает и зачем делать именно это?»

**Решение:** помощник объясняет текущий грейд, показывает карту навыков относительно цели, предлагает один главный шаг и до двух альтернатив. Каждая рекомендация опирается минимум на три фактора: цель/грейд, разрыв и критичность навыка, история участия; дополнительно учитывается доступность. После выполнения видно изменение ожидаемого прогресса.

**Демонстрация:** «На каком я уровне?» → карта «сейчас / требуется» → «Что дальше и почему?» → объяснимая рекомендация → выполнение → обновлённая карта.

**Критерий ценности:** сотрудник без поиска в каталоге может назвать текущий грейд, главный разрыв и следующий шаг. Целевой сценарий — до двух минут; это будущий критерий проверки, не уже измеренный результат.

### Проблема 2. HR не видит, где программа развития не закрывает потребности

Список посещений не объясняет, какие компетенции проседают и у кого нет подходящего следующего шага. Это затрудняет выбор полезных активностей и распределение ресурсов. Расход бюджета описан в кейсе, но финансовых данных для доказательства потерь или ROI недостаточно.

**Решение:** компактная HR-сводка: частые дефициты, сотрудники без рекомендаций, участие по активностям. Помощник визуализирует запрос и объясняет возможное действие HR: уточнить цель, проверить доступность мероприятия или дополнить каталог. Предложение создать мероприятие не выдаётся за существующую запись базы.

**Демонстрация:** «Какие навыки проседают?» → диаграмма → «Кому не хватает следующего шага?» → разрешённый список с причинами → обоснованное действие HR.

**Критерий ценности:** HR определяет приоритетный дефицит и причину отсутствия маршрута; цифры воспроизводятся по базе. Низкое участие не трактуется как низкая результативность сотрудника или намерение уволиться.

### Что уже подтверждено данными

По сохранённому analysis/REPORT.md: 200 сотрудников, 165 с критическим дефицитом; аналитический скрипт подобрал рекомендации 171 сотруднику, 29 остались без них. Карьерная цель есть у 134 сотрудников. Это результаты прежнего аналитического расчёта, не повторная проверка текущего API. Перед демонстрацией пересчитать показатели приложения отдельно.

Дата среза набора — 2026-10-01, позже даты этого плана. Это синтетический срез, не текущая статистика реальной компании. Причины мотивации и эффект нового интерфейса требуют пользовательской проверки.

## 2. Интерфейс: сайдбар, рабочая область, чат справа

Верхнюю навигацию убрать. Основной desktop-экран:

```text
┌──────────────────┬──────────────────────────────┬────────────────────────┐
│ Career Quest     │ Рабочая область              │ AI-помощник            │
│ Профиль          │                              │                        │
│ Роль и грейд     │ Мой уровень                  │ Ответ и источники      │
│ Сотрудник / HR   │ Карта навыков                │ Объяснения и примеры   │
│                  │ Маршрут                      │                        │
│ Обзор            │ Следующий шаг                │ [Карта навыков]        │
│ Карта навыков    │ или HR-сводка                │ [Маршрут] [Что дальше] │
│ Мой маршрут      │                              │                        │
│ История          │ Меняется по команде из чата  │ Поле сообщения         │
└──────────────────┴──────────────────────────────┴────────────────────────┘
```

- Сайдбар: имя/аватар, рабочая роль, грейд, выбор доступного режима, разделы. Для HR: обзор команды, дефициты, отсутствие следующего шага, участие.
- «Сотрудник / HR» показывает только режимы, разрешённые сервером. Свободный выбор синтетического профиля и роли — только в явно обозначенном локальном деморежиме.
- Центр сразу показывает уровень и главный следующий шаг. Польза доступна без обязательного сообщения в чат.
- Справа — свободный вопрос, быстрые команды, объяснение причин, источники и учебные примеры.
- Смена профиля/режима очищает предыдущий чат и визуальное состояние; запоздалый ответ не попадает в новый профиль.
- На узком экране сайдбар сворачивается, чат открывается отдельной панелью. Статусы различаются текстом, а не только цветом; поддерживается клавиатура.
- Пустые разделы «и т. д.» не добавляем. Новые пункты появляются вместе с работающей функцией.

## 3. Сценарии помощника

| Запрос | Ответ справа | Результат в центре |
|---|---|---|
| «На каком я уровне?» | Грейд, цель, дата оценки и главный разрыв | Карточка уровня и требований |
| «Покажи карту навыков» | Сильные стороны и дефициты | Hard/soft-навыки: текущий, ожидаемый, требуемый уровень |
| «Построй маршрут» | Доступные шаги и условия дальнейшего движения | Сейчас → активности → оставшиеся требования → цель |
| «Что делать дальше?» | Основной шаг и до двух альтернатив с причинами | Карточки длительности, формата и ожидаемого эффекта |
| «Почему это, а не Public Speaking?» | Сравнение по цели, критичности и истории | Сравнение допустимых вариантов |
| «Объясни System Design на примере» | Объяснение с пометкой «Учебный пример» | Сохранение карты или поясняющая карточка |
| HR: «Какие навыки проседают?» | Вывод по разрешённой команде | Диаграмма дефицитов |
| HR: «У кого нет следующего шага?» | Причины отсутствия рекомендаций | Разрешённый список и действия HR |

### Факты и база знаний

Источник корпоративных фактов — SQLite: профиль, требования, каталог, история. Для этого объёма достаточно ограниченных SQL-запросов; векторная база не нужна. Ответ показывает ссылки на доступные карточки/записи: требование роли и skill_id, event_id, дата оценки. Backend проверяет цифры, идентификаторы и наличие источников в полученном контексте.

Развёрнутых учебных материалов в наборе нет. Общие объяснения модели помечаются как учебные примеры, не как корпоративная инструкция или факт из базы. Если сведений нет, помощник сообщает об этом. Подключение корпоративных документов — будущий отдельный этап.

### Визуальные результаты

Используем ограниченный набор представлений: level, skill_map, route, next_step, hr_gaps, hr_coverage. Backend проверяет выбранный тип, права и данные; React строит визуальный результат из проверенного JSON.

Не исполняем сгенерированные моделью HTML, JavaScript или SQL. Для эффекта «попросил — увидел карту» достаточно готовых компонентов. Ответ включает текст, представление, проверенные данные/ссылки, источники и статус ok/no_data/fallback. Профиль и права определяются серверной сессией, а не текстом сообщения.

### Что означает «уровень»

- Грейд берётся из профиля; модель не назначает повышение.
- Навык показывается по шкале 0–5 с датой подтверждённой оценки.
- Ожидаемый прирост после активности отделён от подтверждённого уровня и учитывает gain/max_level.
- Готовность к цели — выполненные требования из полного набора требований. Показывать числитель и знаменатель; без требований — «Нет данных». Процент от списка дефицитов использовать нельзя.
- Если цель не задана: «Требования текущей роли; цель не выбрана». Не выдумывать переход на Senior.
- Маршрут не обещает закрыть все разрывы при отсутствии мероприятий. Будущие шаги показывать после проверки prerequisites и доступности; иначе — оставшееся требование.
- Recommendation Score — прозрачная оценка соответствия, не вероятность повышения.

## 4. Существующая основа и необходимые дополнения

Уже есть страницы сотрудника/HR, SQLite, ранжирование, шаблонные объяснения, завершение активности и ожидаемый прогресс. Верхняя навигация находится в frontend/app/layout.tsx. В backend/app/routes.py сейчас нет проверки личности и прав. LLM-чат отсутствует.

| Дополнение | Где | Назначение |
|---|---|---|
| Сайдбар, центр, чат | Текущий Next.js | Новый пользовательский сценарий |
| Полная карта навыков и требований | Текущий career API/движок | Сейчас gaps исключает часть освоенных навыков; этого недостаточно для карты и готовности |
| Доступная история и источники | Текущий API | Раздел «История» и проверяемые объяснения |
| Обработчик чата и проверка результата | Текущий FastAPI/AI-слой | Вопрос → разрешённые факты → текст и визуализация |
| Адаптер модели и серверные настройки | Текущий backend | Ключ, ограничения, таймаут, резервный ответ |
| Сессия и права | Предусмотренный архитектурой Auth | Защита обычных endpoints и чата |
| Причины отсутствия рекомендаций, участие по событиям | Текущий HR API | Сейчас есть список без причин и общая статистика участия |

Новые сервисы, БД, очереди и агентный фреймворк не требуются. Предлагаемый endpoint — POST /api/v1/assistant. Существующие endpoints сохраняются, ответы дополняются. Точные DTO фиксируем при интеграции. Для первой демонстрации чат хранится в рамках сессии без новой таблицы.

До визуализации исправить две найденные особенности: progress.total_required основан на отфильтрованных gaps; projected_gains суммирует gain, а build_gaps применяет общий предел 5 без индивидуального max_level каждого выполненного события. Это локальные исправления достоверности прогресса, не смена архитектуры.

## 5. Приватность и безопасность

### Разграничение прав

| Режим | Разрешено | Запрещено |
|---|---|---|
| Сотрудник | Собственный профиль, история, маршрут; доступный каталог и требования | Чужие профили/вовлечённость и HR-сводка |
| HR | Агрегаты разрешённой команды; минимальные персональные сведения для HR-сценария | Личные чаты, секреты, данные вне своего контура |
| Локальное демо | Переключение синтетических профилей и ролей | Выдавать переключатель за авторизацию; использовать реальные персональные данные |

Для защищённого режима backend получает идентичность из проверенной сессии и хранит права/область команды на сервере. Достаточно заранее созданных тестовых аккаунтов, без регистрации и SSO. Если нужны таблицы учётных записей/сессий — небольшая миграция той же SQLite на этапе Auth. До этого приложение остаётся локальным демо.

Проверки обязательны для employees, career, complete, hr/summary, assistant и источников. Сотрудник не получает общий список коллег. Подмена employee_id, «я HR» в чате и прямой запрос API не обходят ограничения.

### Ключ и внешний контур

В frontend/.env.example указаны OPENAI_API_KEY и NEXT_PUBLIC_API_URL; frontend/.env игнорируется Git. Секрет при подготовке плана не читался, вызовы модели не выполнялись.

При интеграции ключ должен поступать в окружение процесса FastAPI. Описать загрузку серверных настроек и шаблон переменных: frontend/.env автоматически не настраивает Python backend. Значение не попадает в код, браузер, ответы, логи или NEXT_PUBLIC_*. Нахождение ключа в frontend/.env само по себе не доказывает утечку.

Кейс запрещает вынос данных за пределы хакатона и требует внутренний контур. Передачу профилей/истории внешней модели по умолчанию выключить. До включения нужен разрешённый организаторами/владельцем данных контур обработки; обезличивание и наличие ключа сами по себе не отменяют запрет.

Первый показ возможен с локальными проверяемыми ответами и визуальными командами, явно обозначенными как резервный режим, без заявления о работающей LLM. Свободное общение подключается через допустимого провайдера. Локальная модель или внутренний endpoint могут потребовать дополнительной инфраструктуры — это отдельное решение, сейчас его не реализуем.

### Ограничения помощника

- Выбирать разрешённые данные до отправки модели; не передавать всю базу с просьбой скрыть лишнее.
- Контекст минимален: роль, цель, необходимые навыки, агрегаты собственной истории, допустимые события. Имена и подробная история для объяснения не нужны.
- Каталог и сообщения — данные, не инструкции для смены прав. Модель не получает файловый доступ, ключи и произвольные инструменты.
- Чат первой версии только читает и визуализирует. «Заверши курс» открывает карточку действия; запись меняется явной кнопкой через защищённый endpoint с проверкой допустимости и защитой от повторного начисления.
- Ограничить длину сообщений, частоту и время запросов. При таймауте или неверном ответе сохранить карту и показать шаблонное объяснение.
- Не писать чаты/персональные сведения в технические логи. Аудит: время, действие, результат, минимальный идентификатор; доступ ограничен.
- Для cookie-сессий: HttpOnly, Secure при HTTPS и CSRF-защита изменений. CORS не заменяет авторизацию. Приватный кэш изолирован по пользователю, роли и области доступа.
- Не строить публичные рейтинги сотрудников. Для широко доступных агрегатов скрывать малые группы (начальный порог 5, включая связанные фильтры); это снижает риск идентификации, но не заменяет права доступа.

## 7. Последовательность небольших этапов

### Этап 1. Понятный экран сотрудника

Заменить верхнюю навигацию сайдбаром, собрать центр и правую панель. Добавить быстрые команды «Уровень», «Карта навыков», «Маршрут», «Следующий шаг» на текущих данных. Исправить полноту карты и пределы ожидаемого прогресса. Свободный LLM-чат пока не изображать как готовый.

Готовность: команды переключают реальные представления выбранного профиля; видны уровни и причины; выполнение корректно меняет ожидаемый прогресс. Закончен локальный показ решения первой проблемы.

### Этап 2. Права и серверный AI-помощник

Добавить минимальную идентичность и права, затем чат, ограниченный контекст, источники, проверку ответа и адаптер модели. Внешний API подключать только в допустимом контуре. Если его нет, LLM-часть заблокирована этим условием; локальные сценарии продолжают работать.

Готовность: свободный вопрос получает ответ по разрешённым данным и нужную визуализацию; рекомендация объясняется минимум тремя факторами; учебный пример отличается от корпоративного факта; ошибки модели обработаны; чужой профиль недоступен через URL и чат.

### Этап 3. Компактный HR-сценарий

Добавить причины отсутствия следующего шага, участие по мероприятиям, область команды и две визуальные команды HR. Сохранить один компактный экран.

Готовность: HR находит дефицит и отсутствие подходящей активности, видит источник и обоснованное действие. Сотрудник эти сведения открыть не может. Закончен показ второй проблемы.

### Этап 4. Две истории и воспроизводимость

Подготовить короткие сценарии сотрудника и HR на реальных записях синтетического набора. Иллюстративные примеры обозначить отдельно. Проверить дополнительный импорт профилей и истории жюри в исходной схеме, повторный запуск и README; не считать импортёр готовым к этому без проверки.

Готовность: запуск одной командой; дополнительные профили обрабатываются без ручного изменения кода; интерфейс отвечает до 2 секунд, AI до 10 секунд либо в этот срок возвращает понятный резервный ответ.

## 8. Обязательные проверки реализации

1. Сложный профиль: выбор определяется несколькими факторами, а не самым слабым навыком.
2. Карта включает освоенные навыки; готовность использует все требования; неизвестные данные не становятся выдуманной оценкой.
3. Выполнение учитывает gain/max_level; повтор не начисляет прогресс дважды; грейд автоматически не меняется.
4. Нет цели, истории, событий или требований: объяснение без выдуманных маршрутов.
